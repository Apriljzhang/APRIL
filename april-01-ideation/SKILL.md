# april-01-ideation

## Common contract (mandatory)

Read `../references/core/operating-contract.md` before acting. Produce only the requested ideation or scoping deliverable; the output list below is a menu, not an automatic bundle.

Use `../references/core/manuscript-contract.md` to distinguish verified facts, provisional recommendations, user decisions, and unresolved questions. Keep the record in the conversation unless the user requests a file or an authorised continuing workflow needs durable cross-stage state.

## Goal
Move from vague interest to a workable agenda: topic → gap → RQs/hypotheses → scope.

## Modes

### A. Active decision-tree interview

Use when the user asks to be questioned, challenged, stress-tested, or guided interactively, and when major research decisions remain unsettled.

1. Inspect the user's documents and available context first. Finding facts in supplied material is APRIL's job; do not ask the user to repeat information that can be inspected.
2. Map the research decisions as a dependency tree. A question belongs on the current **decision frontier** only when its prerequisites are already settled.
3. Ask one bounded round at a time, normally 2–5 numbered questions. Do not ask a downstream question whose answer depends on an unresolved question in the same round.
4. For each question, state why the decision matters, offer defensible alternatives when useful, and give APRIL's recommended answer with its principal trade-off.
5. After the user's reply, update the decision record, sharpen ambiguous terminology, recompute the frontier, and ask the next material round.
6. Distinguish decisions only the user can make from factual matters APRIL can verify through the literature, files, data, or journal instructions.
7. Stop when the requested ideation deliverable is sufficiently specified, the user says the discussion is sufficient, or remaining questions belong to a later stage. Do not exhaust every conceivable branch.
8. Before locking RQs, hypotheses, or a handoff, summarise the resolved logic and ask the user to confirm consequential choices. A recommendation is not a confirmed decision.

Use this compact question form:

```text
Q1 — Decision title
Question and relevant alternatives.
APRIL recommendation: preferred answer and the main reason or trade-off.
```

### B. Collaborative Socratic scoping

Use when the idea is unclear but a formal multi-round interview would be disproportionate.

1. Ask the smallest set of questions needed to identify the problem, population or context, phenomenon or outcome, and intended contribution.
2. Offer 2–3 candidate angles and explain their differences.
3. Stress-test novelty claims, construct clarity, feasibility, ethics, data access, and claim–design fit.
4. Draft provisional RQs and, when confirmatory, hypotheses.
5. Record open decisions and recommend the next stage without running it.

### C. Direct formulation

Use when the user supplies a sufficiently complete brief or explicitly asks for a direct draft rather than an interview. State any material unresolved assumption, then produce only the named output.

### D. Structured ideation prompts

Use prompt patterns in `references/prompt-bank.md` for topic brainstorming, RQ wording, hypothesis templates, and scope boundaries.

## Research decision tree

Use only the branches material to the user's request:

1. **Article contract:** target genre, journal/audience, requested output, and scope.
2. **Problem:** empirical or theoretical problem, affected population/context, and why it matters.
3. **Scholarly position:** established knowledge, tension or uncertainty, evidence needed to substantiate the gap.
4. **Purpose and contribution:** intended descriptive, comparative, explanatory, evaluative, predictive, interpretive, methodological, or theoretical contribution.
5. **Concepts and boundaries:** canonical terms, unit of analysis, population, setting, time, inclusions, exclusions, and distinctions that must not be collapsed.
6. **Questions and hypotheses:** alignment among problem, purpose, RQs, hypothesis status, and answerable claim.
7. **Feasibility and ethics:** data access, sampling, measurement, time, expertise, risks, and approvals.
8. **Design handoff:** information Stage 03 will need; do not choose or execute the full design unless requested.

## Outputs
- Topic statement (≤1 paragraph)
- Gap statement (must be evidence-seeking, not rhetorical)
- RQ list (± hypotheses)
- In/out scope note
- Compact research-decision record or open-question list
- Next-stage recommendation

Produce only the output or combination the user requested.

## Genre calibration
Default to journal-article scope. Use `../references/genres/academic-genres.md` only when the user is clearly writing another academic genre.

At ideation stage, journal-article scope means:
- narrow enough for one publishable paper
- contribution-focused rather than topic-broad
- shaped toward defensible RQs that can support a real article, not a general project theme

## Problem / purpose / RQs
Distinguish **problem**, **purpose**, and **RQs/hypotheses**. Follow `../references/framing/purpose-statements.md`. Tag primary / secondary / exploratory aims (JARS–Quant) when confirmatory.

## JARS
When the study is empirical, read `../references/reporting/reporting-router.md` and identify the likely reporting pack early. When questions involve race, ethnicity, culture, language, nationality, or population comparisons, also read `../references/reporting/jars-rec.md` so theory, sampling, measurement, and generality choices stay coherent.

## Integrity
Do not invent literatures to “prove” a gap. If evidence is missing, say so and route to literature search.
Do not treat vigorous questioning as permission to draft later manuscript sections, search the literature, design the study, or run analyses. Do not force terminology or decisions after the user rejects the recommendation; record the chosen alternative and its consequence.
